# 검색 흐름 계약

## 목적
이 문서는 검색과 가이드 페이지 읽기 동작의 사용자 노출 계약을 고정한다. 구현과 이 문서가 다르면 구현이 잘못된 것이다.

## 범위
- 검색 결과
- 가이드/문서 상세 페이지 렌더링
- Confluence HTML에서 위키 상세 페이지로 이어지는 페이지 링크 라우팅
- 답변 형식에 대한 검증과 검토 규칙
- 검색 후보 선정과 제외 규칙
- 검색 결과의 대표 페이지와 관련 페이지 분리
- index 페이지 우선 탐색과 하위 페이지 확장 규칙
- 검색 캐시와 버전 갱신 규칙
- 멀티턴 대화 처리와 history 필드 규칙
- 서버 측 추천/관련 페이지 목록 구성 방식
- 질문 intent 분류 시스템

## 검색 대상 규칙
- 검색은 공개 읽기 대상 문서만 기준으로 한다.
- `ops` 문서, `policy` 문서, 온보딩 Q&A 문서는 검색 후보에 넣지 않는다.
- 온보딩 Q&A 문서는 `s*-***` 제목 또는 슬러그 패턴을 사용하면 검색 후보와 추천 페이지 후보에서 제외한다.
- 검색 결과는 반드시 현재 공개 위키 범위 안에서만 구성해야 한다.
- `nav` 문서는 검색 인덱스 확장 단계에서 하위 페이지 후보를 찾는 용도로만 사용한다. `expandSearchContextDocuments` 실행 후 AI 프롬프트에 넘기기 전에 제거해야 한다. AI가 nav 문서를 답변 본문이나 `confluenceData` 인용에 사용하지 않도록 서버에서 필터링한다.

## 관련성 판단 규칙
- 검색 결과의 관련성 판단은 **텍스트 매칭 Gate가 아니라 AI 프롬프트 수준에서 처리**한다.
- `searchResults`에 질문과 의미 있게 관련된 페이지가 없으면 AI는 "현재 위키에 해당 주제에 대한 페이지가 없습니다"라고만 답한다.
- AI가 관련 페이지가 없다고 판단해 `confluenceData`를 비우고 `unsupportedClaims`를 반환하면, FAQ·추천 페이지·관련 페이지를 모두 표시하지 않는다.
- **비교·차이 질문**("A와 B의 차이는?")은 A 페이지와 B 페이지가 각각 있을 때 두 페이지를 함께 사용하는 것이 올바른 동작이다. 단일 페이지에 두 주제가 모두 포함되어야 한다는 조건을 적용하지 않는다.
- 관련성 낮은 문서가 AI context에 포함되지 않도록, lexical scorer에서 다중 토큰 커버리지 점수를 적용한다. 질문의 핵심 토큰 중 일부만 포함하는 문서는 점수가 낮아져 자연스럽게 context에서 밀려난다.
- Stage 1 query-understanding이 usable keyword를 반환하지 못하면, 서버는 원문 질문을 그대로 쓰지 말고 질문어 노이즈를 제거한 fallback 검색 쿼리를 만들어 lexical 검색에 사용한다.
- 하드코딩된 도구 목록(`KNOWN_SUBJECTS` 스타일)이나 한국어→영어 수동 매핑 배열을 늘려 관련성을 개선하는 방식은 사용하지 않는다. 이 방식은 배포 후 새 도구 등록마다 코드 수정이 필요해 유지보수 불가 상태가 된다.

## 검색 탐색 규칙
- 질문 키워드만으로 문서를 바로 고르지 말고, 먼저 `index` 성격의 문서를 빠르게 찾는다.
- `index` 문서를 찾은 뒤에는 그 문서의 하위 페이지와 링크된 상세 페이지를 확장 후보로 삼는다.
- guide 계열 `index` 문서에는 약 5개 정도의 핵심 키워드가 들어 있으므로, 이 키워드와 제목, 슬러그, 요약, 헤딩을 함께 써서 후보를 확장한다.
- `mcp가 뭐야?` 같은 개념 질문은 `mcp 설정하기`처럼 특정 설정 문서로 바로 떨어지지 않도록, index 페이지의 개념 신호를 먼저 살핀다.
- 검색 후보 확장은 `index -> 하위 문서 -> 관련 문서 -> 점수 보정` 순서로 진행한다.
- 점수 보정은 제목, 요약, 헤딩, 본문, 슬러그, 문서 타입, 문서 범위 신호를 조합해서 관련성을 높이는 방향으로 조정한다.
- 질문이 개념인지 설정인지 계획인지에 따라 index 페이지 가중치를 다르게 둔다.
- 개념 질문은 broad overview page가 너무 빨리 setup page로 밀리지 않도록 broad signal을 우선한다.
- 설정/구성 질문은 index 페이지를 거친 뒤 구체적인 실행 문서를 우선한다.
- 계획/준비 질문은 index 페이지와 개요 문서를 우선하고, 세부 절차 문서는 그 다음에 확장한다.

## 검색 답변 규칙
- 화면에 보이는 답변은 설명 문장부터 시작해야 한다.
- `짧답:`, `짧은 답변:`, `간단히:`, `가장 짧게:`, `요약:`, `핵심 요약:` 같은 앞말은 보이는 답변에서 쓰지 않는다.
- 검색 답변은 초·중급 AI 바이브코딩 사용자가 읽어도 이해할 수 있도록 친절하고 설명형이어야 한다.
- 답변은 단답형 summary보다, 먼저 왜 이 문서 가족을 읽는지와 어떤 흐름으로 따라가면 되는지 풀어 주는 블로그식 설명이 더 적절하다.
- 설명 문단은 한 덩어리로 이어 쓰지 않는다. 한 문단에는 1-2문장만 두고, 문단 사이에는 빈 줄을 넣어 아래로 읽히게 한다.
- 기술 용어의 부가 설명은 괄호 안에 넣지 않는다. 설명은 다음 문장이나 바로 아래 짧은 문단으로 분리한다.
- 검색 답변 본문에는 `바로 할 일`, `예시`, `확인`, `확인 포인트`, `주의`, `확인 필요` 같은 고정 섹션 제목을 만들지 않는다.
- 별도 구조화 필드인 `immediateActions`, `exampleCommands`, `verificationChecks`, `cautions`는 별도 스타일 섹션으로 렌더링하지 않는다. 필요한 경우 같은 답변 스타일의 보충 문단/목록으로 보존한다.
- 페이지/문서/가이드/링크의 존재 여부나 위치를 묻는 질문은 주제 설명보다 먼저 검색 결과에서 해당 페이지를 찾았는지 답해야 한다.
- 페이지 찾기 답변은 일치 페이지가 있으면 `찾았습니다` 또는 `있습니다`처럼 확인 결과를 먼저 말하고, `searchResults`의 `href`로 페이지 제목을 링크한다.
- 정확히 일치하는 페이지가 없으면 그 사실을 짧게 말한 뒤, 가장 가까운 문서를 링크한다. 이때 MCP나 CLI 같은 주제 개념 설명으로 답변을 시작하지 않는다.
- 가이드 페이지가 다음 단계로 가장 적절하면, 답변은 무엇을 해야 하는지 설명한 뒤 `이 가이드 페이지를 참고하세요.`라고 이어 간다.
- 실행 가능한 질문이라면, 가독성이 좋아질 때만 짧은 섹션 제목, 체크리스트, fenced code block을 사용할 수 있다.
- `policyNotice`, `immediateActions`, `exampleCommands`, `verificationChecks`, `cautions`, `confluenceData`, `recommendedDocuments` 같은 스키마 이름을 보이는 답변에 드러내지 않는다.
- 검색 화면에 근거 인용문을 노출하지 않는다.
- `concept` 질문은 AI가 `immediateActions`, `exampleCommands`, `verificationChecks`, `cautions`를 채워 반환해도 서버에서 빈 배열로 강제 대체한다. 개념 질문에 행동 섹션이 노출되지 않도록 서버가 보장한다.

## 검색 페이지 순서
1. 답변 설명
2. `추천 페이지`
3. `관련 페이지`

- `추천 페이지`는 대표 가이드 카드 영역이다.
- `추천 페이지`는 하나만이 아니라 여러 장일 수 있다.
- `추천 페이지`의 카드는 강한 순서대로 보여 주며, 첫 카드는 가장 직접적인 대표 문서여야 한다.
- index/overview 계열 문서가 질문의 첫 진입점이면, 그 계열의 첫 문서를 `추천 페이지` 맨 앞에 두고, 같은 가족의 강한 후속 문서를 뒤에 붙인다.
- `관련 페이지`는 보조 읽기 영역이다.
- `추천 페이지`는 답변 다음에 보여야 한다.
- 두 섹션 모두 요약문 없이 페이지 카드 형태로 보여야 한다.
- 검색 결과에 온보딩 Q&A 페이지가 포함되면 안 된다.

## 가이드 선택 규칙
- 대표 페이지는 질문에 가장 잘 맞는 가이드 가족의 첫 페이지여야 한다.
- 대표 페이지는 질문에 잘 맞는 여러 가이드를 순서대로 보여 준다.
- 보조 페이지는 이어서 읽기 좋은 관련 페이지여야 한다.
- 사용자가 `MCP가 뭐지?`처럼 개념을 물으면, `MCP 설정하기` 같은 개요/인덱스 문서를 먼저 보여 주고, 그다음 `Filesystem MCP Setup`처럼 강한 후속 문서를 `추천 페이지` 안에서 함께 보여 줄 수 있다.
- UI는 주제별 하드코딩된 임시 대체 경로를 만들지 않아야 한다.
- 모델이 페이지 연결을 생략했을 때는 fallback 문서를 사용할 수 있으며, AI 추천이 1장만일 때도 같은 검색 후보 풀에서 강한 추천 카드를 보강할 수 있다. 이 경우에도 설명 문장이 아니라 페이지 링크로만 써야 한다.
- 대표 가이드 카드는 사용자가 다음으로 넘어가는 주된 진입점이고, 관련 페이지는 보조 읽기다.
- 가이드 선택 시 새창으로 열어서 검색을 유지해야 한다.
- 검색 후보를 바꾸는 경우, 공개 범위와 제외 규칙을 먼저 이 문서에 반영한 뒤 코드를 바꾼다.
- 검색 캐시는 메모리 기반으로 둔다.
- 캐시는 페이지 ID와 version을 기준으로 갱신하고, TTL 만료 시 다시 채운다.
- 문서 version이 바뀌면 캐시를 무효화하거나 재적재한다.
- 홈 화면 진입 시 필요한 최소 검색 캐시를 미리 데워두는 방식을 허용한다.

## 질문 intent 분류 시스템

검색에는 두 개의 독립적인 intent 분류 함수가 있다. 각각 다른 목적으로 동작한다.

| 함수 | 위치 | 사용 목적 | intent 종류 |
| --- | --- | --- | --- |
| `classifySearchQuestionIntent()` | `aiAsk.ts` | AI 프롬프트 생성 지침 선택 | `page-lookup`, `concept`, `setup`, `broad-planning`, `comparison`, `troubleshooting`, `general` |
| `inferSearchQuestionMode()` | `wikiDocuments.ts` | 문서 검색 랭킹 가중치 결정 | `concept`, `setup`, `planning`, `comparison`, `troubleshooting`, `general` |

두 함수는 같은 질문에서 독립적으로 분류한다. `broad-planning`(AI 프롬프트용)과 `planning`(랭킹용)은 이름이 다르지만 같은 계획형 질문을 각자의 영역에서 처리한다.

`page-lookup`은 AI 프롬프트 전용 intent다. 문서 랭킹은 기존 검색 후보 풀을 그대로 사용하고, 답변 생성만 "페이지 존재/위치 확인" 중심으로 바꾼다.

질문 후보 선정(랭킹)이 완료된 뒤 AI 프롬프트 생성이 시작되므로, 두 분류가 달라도 최종 결과에는 문제가 없다.

### 후보 선정 방식

- `broad-planning`·`concept` 질문: `getTopSearchWikiDocumentsIn`과 `getIndexFirstSearchWikiDocumentsIn`을 병행해 최대 10개 선별 후 `expandSearchContextDocuments`로 최대 14개까지 확장한다.
- 나머지 intent: `getIndexFirstSearchWikiDocumentsIn`(index 우선 확장)만 사용해 최대 8개 선별 후 최대 14개까지 확장한다.
- `page-lookup` 질문: 후보 선정은 기존 `general`/`setup` 계열과 같은 index 우선 확장 후보 풀을 사용하되, AI 답변은 검색 결과 내 일치/근접 문서 확인과 링크 안내에 집중한다.

## 서버 측 추천 목록 구성 규칙

검색 API 응답의 `recommendedDocuments`와 `relatedDocuments`는 서버에서 다음 방식으로 구성한다.

- 완전 미지원 응답(`confluenceData` 없음 + `unsupportedClaims` 있음)은 두 배열을 모두 비운다. 클라이언트도 fallback 추천과 FAQ를 추가하지 않는다.
- AI가 보이는 답변에서 "현재 위키에 해당 주제에 대한 페이지가 없습니다"처럼 no-page 문구를 반환했는데 `unsupportedClaims`를 비워 둔 경우, 서버는 이를 완전 미지원 응답으로 정규화해야 한다.

### 추천 페이지 (`recommendedDocuments`, 최대 4개)
- **docType이 `guide` 또는 `page`인 문서만 후보가 될 수 있다 (선택 방식, 제외 방식 아님).** `nav`/`ops`/`policy`/`playbook`은 물론, `faq`/`library` 등 다른 모든 docType도 이 목록에는 나오지 않는다 — FAQ는 검색 화면의 별도 `faq` 섹션에서만 노출된다. docType을 하나씩 나열해 제외하는 방식은 새 docType이 추가될 때마다 놓치기 쉬우므로(예: `faq` 계열 Index 문서가 `nav`가 아니라는 이유로 새어나간 사례, 2026-07-28), "허용된 두 타입만 선택"하는 방식으로 고정한다.
1. AI가 선택한 `recommendedPages` 중 위 조건을 만족하는 결과를 우선 사용한다.
2. AI가 선택하지 않았거나 결과가 없으면, 랭킹 상위 후보(`getIndexFirstSearchWikiDocumentsIn`, 동일하게 `guide`/`page`만) 로 보완한다.

### 관련 페이지 (`relatedDocuments`, 최대 4개)
1. 랭킹 상위 후보(`guide`/`page`만) 중 `recommendedDocuments`에 이미 포함된 것을 제외한 나머지다.

### 문서 상세 페이지의 추천 페이지 (`ArticleAskPanel`의 `suggestedNextPages`)
- 위와 동일하게 docType이 `guide` 또는 `page`인 문서만 노출한다.

AI 원시 출력의 `recommendedPages` 필드는 서버에서 제거되고 클라이언트에 전달되지 않는다.

## 멀티턴 대화 규칙

검색은 같은 세션에서 여러 질문을 연속 처리하는 멀티턴 대화를 지원한다.

- 클라이언트는 완료된 이전 질문/답변을 최근 3턴까지 `history`에 담아 요청에 포함한다.
- 서버는 `history`를 `buildSearchFollowUpQuestion()`으로 합성해 후속 질문을 재구성한다. 이 결과가 캐시 키와 검색 질문으로 사용된다.
- 클라이언트는 같은 세션에서 이미 처리한 질문(정규화 기준)을 중복 요청하지 않는다.
- `history`는 AI 프롬프트 생성과 검색 후보 선정 양쪽에 반영된다.

## 가이드 페이지 규칙
- 가이드 콘텐츠 안의 Confluence 링크는, 일치하는 로컬 위키 페이지가 있으면 위키 상세 경로로 연결해야 한다.
- 가이드 페이지는 코드 블록을 가능한 경우 언어와 줄 수가 보이는 코드 프레임으로 렌더링해야 한다.
- 가이드 페이지는 callout, note, warning, panel을 시각적으로 구분되는 블록으로 렌더링해야 한다.
- 본문 안에 이미 같은 제목과 요약이 있으면 중복 표시를 줄여야 한다.


## 검증 규칙
- 보이는 답변은 접두사 라벨로 시작하면 안 된다.
- `추천 페이지` 섹션은 `관련 페이지`보다 위에 있어야 한다.
- 일치하는 위키 페이지가 있으면 가이드 페이지는 raw Confluence 링크가 아니라 위키 상세 경로를 열어야 한다.
- 페이지 렌더링은 변경이 반영될 때마다 다시 확인해야 한다.
- 검색 후보에 온보딩 Q&A 페이지가 섞이면 안 된다.
