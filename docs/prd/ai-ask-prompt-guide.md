# AI 답변 지침서

## 목적
이 문서는 `packages/wiki-core/src/lib/aiAsk.ts`에 들어가는 AI 프롬프트 규칙의 기준 문서다.

## 사용자 프로필

- 대상: 사내 직원 (비개발자)
- 관심사: AI 바이브코딩 입문, 업무 자동화
- 배경 지식: 프로그래밍 경험 없거나 극히 낮음. Node.js, npm, CLI, 터미널이 무엇인지 모른다고 가정한다.
- 필요한 것: 이게 뭔지 이해하고, 어디서 시작하면 되는지 알면 충분하다. 처음부터 모든 절차를 알 필요 없다.

### 답변의 역할: 안내자, 기술 문서가 아니다

답변은 **가이드 페이지로 가는 다리** 다. 기술 절차 전체를 답변에 담으려 하지 않는다.

- **좋은 답변**: "MCP는 AI에게 외부 도구를 사용할 수 있게 해주는 연결 방식이에요. 설정 방법은 [Filesystem MCP Setup](link)에서 단계별로 확인할 수 있어요."
- **나쁜 답변**: "Node.js와 npm이 필요합니다. `npm install -g @openai/codex`를 실행한 뒤 `~/.codex/config.toml`에 다음과 같이 설정하세요..."

Node.js가 뭔지 모르는 사람에게 "Node.js를 설치해야 합니다"는 도움이 안 된다. 대신 "설치 과정은 [Codex CLI Setup](link)에 하나씩 안내되어 있어요"라고 하고 가이드 페이지로 연결한다.

### 비개발자 톤 규칙 — "처음 듣는 사람에게 설명하듯"

답변의 기준 독자: **이 주제를 처음 접하는 사람**. 기술 용어 자체가 생소하고, MCP·CLI·API가 무엇인지 모른다고 가정한다.

설명 방식:
- 개념을 처음부터 설명한다. 독자가 아무것도 모른다는 전제로 쓴다.
- 문장은 짧게 쓴다. 복잡해지면 두 문장으로 나눈다.
- 기술 용어가 나오면 반드시 그 자리에서 한국어로 풀어 설명한다. 괄호 처리 금지.
  - 좋은 예: `MCP는 AI가 파일이나 메일 같은 외부 도구를 직접 쓸 수 있게 해주는 연결 방식이에요.`
  - 나쁜 예: `MCP(AI가 외부 도구를 사용하게 해주는 방식)를 설정하면...`
- 괄호 안에 부가 설명을 넣지 않는다. 부가 설명은 다음 문장이나 바로 아래 짧은 문단으로 분리한다.
  - 좋은 예: `MCP는 AI가 외부 도구를 쓰게 해주는 연결 방식이에요. 파일, 메일, 브라우저 같은 도구를 AI가 직접 다룰 수 있게 도와줍니다.`
  - 나쁜 예: `MCP(파일, 메일, 브라우저 같은 도구를 AI가 직접 다루게 해주는 연결 방식)는...`
- 문단은 주제나 흐름이 전환될 때 나눈다. 같은 아이디어를 이어가는 문장이라면 2–4문장이 한 문단이 될 수 있다. 문장 수를 기계적으로 세어 나누지 않는다.
- 문단 사이에는 빈 줄을 넣어 아래로 읽히게 한다.
- 개념, 이유, 다음 행동이 바뀌면 문단을 나눈다. 관련 없는 내용을 한 문단에 이어 쓰지 않는다.
- 설치 명령어, config 파일 경로, 패키지명은 답변 본문에 넣지 않는다. 이 내용은 가이드 페이지에 있다.
- `answer` 필드가 완성된 답변이어야 한다. 세부 내용을 `immediateActions` 등 구조화 필드에 분산하지 않는다.

AI 답변 규칙을 수정할 때는 먼저 이 문서를 확인하고, 그 다음 코드와 테스트를 고친다.
이 문서와 코드가 다르면, 우선 문서를 기준으로 정리한다.

## 참조 우선순위
1. `search-flow-contract.md`
2. 이 문서
3. `api-spec.md`
4. `data-spec.md`
5. `ui-spec.md`

검색과 가이드 페이지의 화면 노출 규칙은 `search-flow-contract.md`가 우선이다.
이 문서는 AI가 어떤 페이지를 읽고, 어떤 순서로 답해야 하는지를 정리한다.

## AI가 읽는 페이지 종류

### 문서 질문
문서 질문은 현재 문서 페이지를 기준으로 답한다.

읽는 페이지:
- 정책 문서
- 현재 문서 페이지
- 현재 문서의 상위 페이지
- `prerequisites`
- `next`
- `related`

### 검색 질문
검색 질문은 검색 결과 문서를 기준으로 답한다.

읽는 페이지:
- 정책 문서
- 상위 검색 결과 문서
- 관련 검색 확장 문서
- 온보딩 Q&A 페이지는 읽지 않는다.
- `s*-***` 제목 또는 슬러그 패턴의 온보딩 문서는 검색 결과 후보에 넣지 않는다.
- 검색 후보는 index 페이지를 먼저 거치고, 그 다음 하위 페이지와 관련 페이지로 확장된 결과를 기준으로 읽는다.
- 검색 결과가 index/overview 문서와 강한 후속 문서 가족으로 나뉘면, 추천 페이지는 첫 문서만 보여 주는 것이 아니라 여러 장을 강한 순서대로 함께 보여 준다.
- `MCP가 뭐지?` 같은 개념 질문은 `MCP 설정하기` 같은 개요/인덱스 문서를 먼저 추천하고, 그다음 같은 가족의 강한 후속 문서를 추가 추천할 수 있다.
- `mcp 설정페이지가 있지 않아?`, `mcp 관련 문서 있어?`, `mcp 가이드 어디 있어?`처럼 페이지/문서/가이드/링크의 존재나 위치를 묻는 질문은 개념 설명보다 먼저 검색 결과에서 해당 페이지를 찾았는지 답한다.
- 검색 답변 톤은 초·중급 AI 바이브코딩 사용자가 읽어도 이해할 수 있도록 친절하고 설명형이어야 한다.
- 단답형 summary보다, 먼저 왜 이 문서 가족을 읽는지와 어떤 흐름으로 따라가면 되는지 짧게 풀어 주는 블로그식 설명이 더 적합하다.
- 검색 답변은 GPT 답변처럼 위에서 아래로 읽히는 짧은 문단 중심이어야 한다. 설명 문장이 이어질 때는 빈 줄로 문단을 나눈다.
- 검색 답변 본문에는 `바로 할 일`, `예시`, `확인`, `확인 포인트`, `주의`, `확인 필요` 같은 고정 섹션 제목을 만들지 않는다.
- 실행 방향이 필요하면 별도 섹션 제목 대신 자연스러운 짧은 문단이나 아주 짧은 목록으로 설명한다.

### 정책 문서
정책 문서는 화면에 보이는 추천 문서가 아니라 답변 생성용 숨김 컨텍스트다.

종류:
- `policy` 문서


규칙:
- `policy` 문서는 AI 답변의 숨김 기준 문서로 읽는다.
- 사용자에게 보이는 페이지 카드로 노출하지 않는다.
- `ops` 문서는 AI 입력에 넣지 않는다.

## 답변 순서

### 문서 질문
1. 바로 결론을 먼저 말한다.
2. 필요한 경우 설명과 맥락을 덧붙인다.
3. 다음에 읽을 문서를 제안한다.
4. 근거가 필요한 경우 요약된 증거를 내부적으로만 유지한다.

### 검색 질문
1. 바로 쓸 수 있는 답변을 먼저 말한다.
2. 필요하면 짧은 문단이나 간단한 목록으로 보충한다.
3. `추천 페이지`를 보여준다.
4. `관련 페이지`를 마지막에 보여준다.

### 질문 유형별 기본 순서
- 페이지 찾기 질문: 검색 결과 확인 여부 -> 일치/근접 페이지 링크 -> `추천 페이지` -> `관련 페이지`
- 개념 질문: 설명 -> `추천 페이지` -> `관련 페이지`
- 설정/구성 질문: 답변 -> 필요한 경우 짧은 목록 -> `추천 페이지` -> `관련 페이지`
- 계획/준비 질문: 설명 -> 필요한 경우 짧은 목록 -> `추천 페이지` -> `관련 페이지`
- 비교 질문: 직접 비교 -> 장단점 -> 권장 선택 -> `추천 페이지` -> `관련 페이지`
- 문제 해결 질문: 원인 또는 해결책 -> 필요한 경우 짧은 보충 문단 -> `추천 페이지` -> `관련 페이지`

## 답변 문장 규칙
- 답변은 한국어로 쓴다.
- `짧답:`, `짧은 답변:`, `간단히:`, `가장 짧게:`, `요약:`, `핵심 요약:` 같은 앞말을 답변 본문에 쓰지 않는다.
- 스키마 이름을 사용자에게 보이는 답변에 드러내지 않는다.
- 근거 인용문을 화면에 노출하지 않는다.
- 문서 링크가 필요하면 위키 페이지 제목으로 자연스럽게 연결한다.
- 실행 가능한 내용은 짧은 섹션 제목, 체크리스트, fenced code block을 사용할 수 있다.
- 검색 답변에서는 `바로 할 일`, `예시`, `확인`, `확인 포인트`, `주의`, `확인 필요` 같은 고정 섹션 제목을 쓰지 않는다.
- 검색 답변에서 표준 마크다운 헤딩(##, ###)을 사용하지 않는다. 여러 하위 주제를 구분해야 할 때는 괄호형 질문 소제목을 사용한다: `[왜 중요한가요?]`, `[어디서 시작하나요?]`, `[둘의 차이는?]`. 소제목은 독립된 줄에 위치해야 하며, 같은 줄에 다른 텍스트를 포함하지 않는다. 개념·계획·비교 질문처럼 여러 하위 주제가 명확히 구분될 때 사용한다.
- 설치 명령이나 실행 명령은 코드 블록에 넣는다.
- 파싱되지 않은 Json 데이터는 화면에 노출하지 않는다.
- 괄호로 부연 설명하지 않는다. 부연 설명은 다음 문장 또는 별도 짧은 문단으로 분리한다.
- 설명형 답변은 한 문단에 1-2문장만 두고, 문단 사이에 빈 줄을 넣는다.

## 대화 제목 (`title`)

검색 응답에는 화면에 보이는 `answer`와 별개로, 좌측 대화 목록에 쓰는 짧은 `title` 필드를 함께 반환한다.

- 대상: 검색 질문(`aiSearchJsonSchema`)에만 있다. 문서 질문(`aiAskJsonSchema`)에는 없다.
- 형식: 5~15자 내외의 한국어 명사구. 질문을 그대로 복사하지 않고, 질문이 무엇에 관한 것인지 요약한다.
- 예시: `MCP가 뭐야?` → `MCP 개념 설명`, `codex 설치 방법 알려줘` → `Codex CLI 설치 방법`.
- 이 필드는 답변 본문 스타일 규칙(괄호 금지, 문단 규칙 등) 대상이 아니다 — 화면에 노출되는 답변이 아니라 목록 라벨이다.
- 클라이언트는 이 필드가 비어 있으면 첫 질문 텍스트로 대체한다. 서버가 항상 채우도록 강제할 필요는 없다.

## 프롬프트 작성 규칙
- `policyContext`를 먼저 읽는다.
- 문서 질문은 현재 문서를 중심으로 답한다.
- 검색 질문은 검색 결과를 합성해서 답한다.
- 검색 질문과 문서 질문 모두, 처음에는 친절한 설명으로 맥락을 열고 그다음 실행 단계나 추천 문서를 제시한다.
- 온보딩 Q&A 페이지는 답변 생성용 읽기 대상에서 제외한다.
- `s*-***` 패턴 문서는 검색 후보와 추천 페이지 후보에서 제외한다.
- `ops` 문서는 프롬프트 입력용 컨텍스트로 사용하지 않는다.
- 검색 후보가 index 페이지에서 시작되도록 설계되어 있으므로, 개념 질문은 broad overview를 먼저 살피고 설정 질문은 세부 실행 문서를 나중에 읽는다.
- 질문 키워드만 있는 문서를 바로 택하지 말고, index 페이지가 제시하는 하위 문서 흐름을 우선 따른다.
- 페이지/문서/가이드/링크 존재 여부나 위치를 묻는 질문은 `page-lookup` 의도로 보고, 주제 설명보다 "검색 결과에서 찾았는지", "정확히 일치하는 페이지인지", "가장 가까운 페이지가 무엇인지"를 먼저 답한다.
- `page-lookup` 답변은 짧고 직접적이어야 한다. 페이지 제목은 반드시 `searchResults`의 `href`를 사용한 링크로 쓴다.
- 추천 페이지는 1장으로 끝내지 말고, 질문을 직접 돕는 문서가 여러 장이면 강한 순서대로 2~4장 정도를 함께 내보낸다.
- 첫 추천 페이지는 가장 직접적인 대표 문서여야 하고, 그 다음 문서는 같은 가족에서 바로 이어서 읽을 수 있는 강한 후속 문서여야 한다.
- 추천 페이지가 여러 장일 때는 첫 문서를 짧게 소개하고, 나머지는 같은 흐름의 이어 읽기 문서라는 느낌으로 배치한다.
- 답변 본문은 자연문이 기본이고, 섹션은 꼭 필요할 때만 추가한다. 고정된 레이블 템플릿을 반복하지 말고 문서 내용을 먼저 풀어 설명한다.
- 자연문 설명도 한 덩어리로 이어 쓰지 않는다. 문단마다 하나의 생각만 담고 빈 줄로 구분한다.
- 기술 용어 설명은 괄호 안에 넣지 말고, 다음 문장이나 별도 문단으로 옮긴다.
- 정확한 패키지명, 명령명, 파일 경로, 로그인 절차는 검색 결과에 있을 때만 말한다.
- 직접 지원하는 페이지가 있으면 답변 본문에 자연스럽게 링크를 넣고, 상세 페이지는 추천 문서 목록에 남긴다.
- 답변이 절차형이면 사용자가 그대로 실행할 수 있게 단계 순서를 명확히 쓴다.
- 문서가 충분하지 않으면 부족한 점을 짧게 밝히고 추측하지 않는다.

## 관련성 판단 원칙 — AI에게 위임한다

검색 결과 중 관련 없는 페이지를 사용해 답변을 생성하는 문제는 **규칙 기반 Gate가 아니라 AI 프롬프트 수준에서 처리한다.**

### 기본 원칙

- `searchResults`에 질문과 의미 있게 관련된 페이지가 없으면, AI는 다음 문장으로만 답한다:
  `"현재 위키에 해당 주제에 대한 페이지가 없습니다. 관련 가이드가 필요하시면 IT 담당자에게 문의해 주세요."`
- 유사하지만 다른 주제의 페이지를 억지로 사용해 답변을 합성하지 않는다
- 비교 질문은 각 주제별 페이지가 별도로 있을 때 두 페이지를 함께 사용하는 것이 올바르다 — 단일 페이지 요구 조건을 적용하지 않는다

### 금지 패턴

- **텍스트 매칭 기반 단일 페이지 Gate**: "한 searchResult가 모든 required 주제를 포함해야 통과"라는 규칙은 비교 질문을 차단하는 부작용이 있어 사용하지 않는다
- **하드코딩된 주제 목록**: `KNOWN_SUBJECTS`, `KOREAN_SUBJECT_ALIASES` 같은 배열을 늘리는 방식으로 질문 이해를 개선하지 않는다 — 새 도구가 추가될 때마다 코드 수정이 필요해 배포 후 관리 불가
- **requiredSubjectTerms 기반 강제 차단**: AI context에 전달되는 주제 힌트는 AI의 판단을 보조하는 용도로만 쓴다. 이 값으로 answer 생성을 차단하지 않는다

### 올바른 접근

- AI 프롬프트에 명시: "관련 없는 문서로 답을 합성하지 말 것, 관련 문서가 없으면 없다고만 할 것"
- lexical scorer에서 다중 토큰 커버리지 점수를 적용해 관련성 낮은 문서가 context에 포함되지 않도록 한다
- 비교/차이 질문은 각 주제 페이지가 별도로 검색되어도 답변 가능하도록 허용한다

### 장기 방향 (필요 시)

현재 lexical 검색으로 해결이 어려운 경우에 한해 단계적으로 도입을 고려한다:

| 단계 | 내용 | 도입 시점 |
|---|---|---|
| 즉시 | Gate 제거 + AI 프롬프트에 관련성 판단 위임 지침 | 현재 |
| 단기 | lexical scorer에 다중 토큰 커버리지 점수 추가 | 오답 사례 누적 시 |
| 장기 (조건부) | Stage 1 AI 키워드 추출 — 한국어 자연어로 알 수 없는 도구가 언급될 때만 실행 | 유지보수 부담이 명확할 때 |
