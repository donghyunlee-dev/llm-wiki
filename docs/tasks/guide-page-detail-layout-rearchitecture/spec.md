# guide-page-detail-layout-rearchitecture Spec

## Problem Statement
직전 두 차례(`docs/tasks/guide-page-toc-sidebar-refresh/`)의 TOC 분리 시도가 모두 `position: fixed` + 뷰포트 퍼센트 기반 `calc()`를 사용해, 스크롤바 폭 차이로 인한 오차(Codex가 반복적으로 발견)와 "컨텐츠가 TOC 제외 영역이 아니라 전체 화면 기준으로 중앙 정렬되는" 회귀를 반복적으로 발생시켰다. 사용자가 3번째 재요청하며 정밀한 최종 수정을 요구했다. 추가로 다음 문제가 실제 화면(사용자 제공 스크린샷)에서 확인됨: 목차를 아래로 스크롤했다가 위로 올리면 "목차" 라벨이 보이지 않음, 문서 페이지 검색 버튼 위치가 깨져 보임, 홈 화면의 미완성 blueprint 영역이 노출됨, `[Type]` 대괄호 접두어가 일부 화면(문서 내 인라인 링크 등)에서 여전히 노출됨.

## Business Context
사용자가 반복 재작업에 대한 불만을 명확히 표현("벌써 3번째 반복") — 이번엔 근본 원인(뷰포트-상대 calc의 스크롤바 오차)을 제거하는 구조 변경으로 대응. Playwright 실측 검증과 Codex 리뷰를 모두 거쳐야 함을 명시적으로 요구받음.

## Scope
1. TOC(목차)를 공용 `site-shell`(모든 라우트가 공유하는 `max-w-6xl` 중앙 컨테이너) 밖으로 구조적으로 분리 — `ArticlePage`/`StartingGuidePage` 라우트를 `CardLayout` 밖, `AppLayout`의 직계 자식으로 이동(기존 `SearchPage`와 동일 패턴)하고, 순수 flex 2단 레이아웃(계산식 없음)으로 재구성.
2. 목차 내부 스크롤 시 "목차" 라벨이 사라지는 버그 수정 — 라벨을 스크롤 박스 밖으로 분리.
3. 컨텐츠는 목차를 제외한 영역에서 독립적으로 중앙 정렬(뷰포트 전체 폭 기준, site-shell의 좁은 max-width에 갇히지 않음).
4. 문서 페이지 플로팅 검색(Ask) 버튼 위치를 새 레이아웃에 맞춰 재계산.
5. 홈 화면의 미완성 "blueprint"(프로젝트 설계 CTA) 섹션 숨김 처리.
6. `[Type]` 대괄호 접두어 제거 필터의 누락 지점(문서 내 인라인 링크, 그래프 포커스바, 정책 출처 링크) 보완 — 링크의 `href`/매칭 로직은 절대 변경하지 않고 표시 텍스트만 처리.

## Out Of Scope
- `ProjectDetailPage`, `/guides`·`/library`·`/faq` 목록 페이지, `/guides/map` 그래프 페이지의 레이아웃 — TOC가 없는 페이지는 변경하지 않음.
- Guide Index Graph 페이지의 노드 라벨 약어 파싱 로직(`parseNodeLabel`) — 대괄호를 의도적으로 타입 약어 추출에 사용하는 별도 기능이라 건드리지 않음.
- Blueprint CTA 자체의 재설계 — 이번엔 숨김 처리만, 재작업은 별도 진행.

## User Or Operator Scenarios
- 데스크톱(xl 이상)에서 가이드/문서 상세 페이지를 열면, 목차가 화면 우측 끝(공용 padding만큼의 여백)에 붙어 있고, 본문은 목차를 제외한 영역에서 중앙 정렬되어 보인다.
- 태블릿/모바일(xl 미만)에서는 목차가 본문 아래에 일반 문서 흐름으로 쌓인다.
- 헤딩이 많은 문서에서 목차 하단 항목을 클릭해도 "목차" 라벨은 항상 보인다.
- 검색(Ask) 버튼은 본문 폭과 정확히 일치하며, 넓은 화면에서도 폭이 어긋나지 않는다.
- 홈 화면에는 미완성 blueprint 영역이 보이지 않는다.
- 문서 내 인라인 링크, 그래프 포커스바, 정책 출처 링크 등 어디에서도 "[Guide]"류 접두어가 중복 노출되지 않으며, 모든 링크는 정상 동작한다.

## Acceptance Criteria
- AC1: `ArticlePage`/`StartingGuidePage`가 `CardLayout`/`site-shell` 밖에서 렌더링되며, `/guides/map` 등 인접 라우트가 라우팅 충돌 없이 정상 동작한다.
- AC2: xl 이상에서 TOC가 뷰포트 우측 끝(공용 padding만)에 위치하고, 본문은 TOC를 제외한 flex 영역 내에서 `mx-auto`로 중앙 정렬된다 — 계산식(calc/뷰포트%) 없이 순수 flex로 구현되어 스크롤바 폭 오차가 발생하지 않는다.
- AC3: xl 미만에서 TOC는 본문 아래 일반 문서 흐름으로 쌓인다.
- AC4: 긴 목차에서 하단 항목 클릭 후에도 "목차" 라벨이 항상 보인다(구조적으로 스크롤 박스 밖에 위치).
- AC5: Ask 도크가 모든 브레이크포인트에서 본문 폭과 정확히 일치한다(픽셀 단위 확인).
- AC6: 홈 화면에 blueprint 섹션이 렌더링되지 않는다.
- AC7: 인라인 링크/그래프 포커스바/정책 출처 링크의 표시 텍스트에서 접두어가 제거되며, 모든 링크의 `href`/매칭 로직은 기존과 동일하게 동작한다(회귀 없음).
- AC8: `pnpm test`(web+wiki-core)/`typecheck`/`build` 통과.
- AC9: Playwright로 1280/1920/800/390px + 라이트·다크 확인, Codex 크리티컬 리뷰 수행 및 발견 사항 반영.

## Edge Cases
- TOC가 없는 문서(`StartingGuidePage`에서 헤딩 0개) — flex row/TOC 없이 본문만 렌더링.
- 매우 넓은 화면(1920px+)에서 본문과 TOC 사이에 큰 여백이 생기는 것은 "TOC는 화면 끝에, 컨텐츠는 별도로 중앙 정렬"이라는 요구사항의 자연스러운 결과로 허용.
- `ProjectDetailPage` 등 TOC 없는 페이지가 사용하는 `.article-layout` 클래스는 원래 정의를 유지해 영향받지 않아야 함(Codex가 이전 라운드에서 발견한 회귀 패턴 재발 방지).

## Assumptions
- `site-main`(CardLayout이 없는 라우트가 이미 사용 중인, `SearchPage`의 선례)은 max-width 제약이 없어 전체 폭을 그대로 사용할 수 있다.
- 사용자가 명시한 "TOC는 우측 끝에 붙어 있고 컨텐츠는 제외 영역에서 중앙"은 문자 그대로의 구조적 분리를 의미하며, 넓은 화면에서 발생하는 시각적 여백 차이는 감수한다.

## Clarifications
- 별도 브레인스토밍 세션 없이 사용자의 상세하고 반복적인 지시(5개 항목, 정밀 검증 요구)를 직접 스펙으로 정리 — 이미 3차 반복이라는 문맥상 추가 확인 질문 없이 즉시 진행.
