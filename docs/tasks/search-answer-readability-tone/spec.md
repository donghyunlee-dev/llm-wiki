# Search Answer Readability Tone Spec

## Problem Statement
- 검색 결과 답변의 설명 문장이 한 덩어리로 이어져 보여 읽기 어렵다.
- 답변이 기술 용어를 괄호로 풀어 설명하는 경우가 많아 흐름이 끊긴다.
- 페이지나 문서의 존재 여부를 묻는 질문도 개념/설정 질문처럼 답하면서, 사용자가 원하는 "해당 페이지를 찾아보고 있는지"가 먼저 드러나지 않는다.
- 검색 입력창, 사용자 질문, AI 답변 본문의 글자 크기가 비슷하고 작아 읽기 어렵다.

## Business Context
- 검색 결과는 비개발자 사내 직원이 첫 답변으로 읽는 화면이다.
- 답변은 GPT 답변처럼 위에서 아래로 문단 단위로 읽혀야 한다.

## Scope
- 검색 답변 프롬프트가 짧은 문단과 빈 줄 분리를 명확히 요구하도록 조정한다.
- 기술 용어 부가 설명은 괄호가 아니라 다음 문장이나 별도 짧은 문단으로 쓰도록 지침을 강화한다.
- 검색 답변 렌더링에서 긴 설명 문단이 한 덩어리로만 보이지 않도록 문단 분리 보정을 추가한다.
- 검색 답변 본문에는 `바로 할 일`, `예시`, `확인`, `확인 포인트`, `주의`, `확인 필요` 같은 고정 섹션 제목을 생성하지 않는다.
- 검색 화면은 `immediateActions`, `exampleCommands`, `verificationChecks`, `cautions` 구조화 보조 필드를 버리지 않고, 필요할 때 같은 답변 스타일의 자연스러운 보충 문단/목록으로 렌더링한다.
- 페이지/문서/가이드/링크 존재 여부나 위치를 묻는 검색 질문은 별도 `page-lookup` 의도로 분류하고, 개념 설명보다 검색 결과 내 일치/근접 페이지 여부와 링크를 먼저 답한다.
- 검색 입력 텍스트, 사용자 질문 텍스트, AI 답변 본문 텍스트의 크기를 분리하고, AI 답변 본문과 제목성 텍스트를 더 크게 보여준다.
- AI 답변 지침서를 같은 규칙으로 업데이트한다.

## Out Of Scope
- 검색 후보 선정, 추천/관련 페이지 선정, 문서 랭킹 변경.
- 검색 결과 카드 디자인 변경.
- Confluence 데이터 구조 변경.

## User Or Operator Scenarios
- 사용자가 검색 결과 답변을 읽을 때 설명 문장이 적절한 문단으로 나뉘어 보인다.
- 기술 용어 설명이 괄호 안에 끼어들지 않고 다음 문장이나 짧은 부가 설명으로 이어진다.
- 사용자가 `mcp 설정페이지가 있지 않아?`처럼 묻는 경우, 답변은 MCP 개념 설명이 아니라 해당 페이지를 검색 결과에서 찾았는지와 연결 가능한 페이지 링크를 먼저 알려준다.
- 사용자가 검색 결과 화면을 볼 때 입력 텍스트, 질문 말풍선, AI 답변, 답변 내 제목성 텍스트가 서로 다른 크기와 굵기로 구분된다.

## Acceptance Criteria
- 검색 프롬프트 지침에 문단당 1-2문장, 문단 사이 빈 줄, 긴 설명의 문단 분리 규칙이 포함된다.
- 검색 프롬프트 지침에 괄호 설명 금지와 대체 방식이 포함된다.
- 긴 단일 설명 문단은 검색 답변 UI에서 여러 문단으로 보정되어 렌더링된다.
- 답변 본문에 액션/확인/주의 계열 고정 섹션이 새로 생성되지 않는다.
- 구조화 보조 필드가 응답에 있어도 검색 화면에 별도 스타일 섹션으로 노출되지 않고, 내용은 같은 답변 스타일로 보존된다.
- 페이지 존재/위치 질문은 `page-lookup`으로 분류되고, 프롬프트는 주제 설명을 길게 하지 말고 일치 또는 근접 문서 링크를 답하도록 요구한다.
- 검색 입력창 텍스트와 placeholder는 기존보다 크게 보이고, 사용자 질문과 AI 답변 본문은 서로 다른 크기로 구분된다.
- 답변 내 markdown heading은 본문보다 크고 굵게 보인다.
- 관련 테스트가 추가 또는 갱신된다.

## Edge Cases
- 번호 목록, 불릿 목록, 코드 블록, 표는 문단 보정으로 깨지면 안 된다.
- 링크가 포함된 문장은 링크 마크다운이 유지되어야 한다.

## Assumptions
- 모델이 지침을 지키지 못하고 긴 단일 문단을 반환할 수 있으므로 UI 보정이 필요하다.
